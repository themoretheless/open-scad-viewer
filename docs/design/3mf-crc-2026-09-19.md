# Shared CRC32 for 3MF packaging

Both `gcode-core` and `polygon-core` maintained the same per-byte, eight-bit
CRC32 loop. They now import `crc32fast::hash`. Version 1.5.2 was already locked
and in the workspace dependency graph through flate2; the lockfile change only
adds two direct dependency edges. ZIP layouts, CRC polynomial, compression,
byte limits and G-code validation are unchanged. No new common utility crate
or hand-maintained CRC table was introduced.

## Native measurement

Build `bench_package_crc` in release mode, then execute the binary separately:

```sh
cargo build --offline --locked --release --manifest-path crates/Cargo.toml \
  -p gcode-core --example bench_package_crc
crates/target/release/examples/bench_package_crc tmp/performance/package-crc-current
```

The example packages fixed repeated ASCII G-code without compression, with
three warmups and nine samples. Source construction, byte-equality checks and
archive writes are outside timing. Allocation and packaging are timed; final
archive destruction is outside timing. It saves complete archives, not merely
their CRCs, for independent before/after comparison. It does not generate or
slice a model, and it is not a browser export benchmark.

macOS arm64, Apple M4 Max, pinned release Rust toolchain. No own builds/tests
overlapped the measured runs; a process check before baseline found no matching
compiler/test processes. Same source bytes and output archives in both variants:

| Input bytes | Before median ms | After median ms | Repeat median ms |
| ---: | ---: | ---: | ---: |
| 65,520 | 0.6075 | 0.0148 | 0.0095 |
| 1,048,560 | 9.5510 | 0.2472 | 0.1305 |
| 3,145,720 | 28.5380 | 0.4696 | 0.3353 |

The variation between modified runs is material at these short durations.
Use the samples, not a universal speedup multiplier. Source and archives are
held warm; network, cold process initialization and real printer job generation
are excluded. Evidence: `tmp/performance/package-crc-{before,after,repeat}.jsonl`
and the corresponding directories of `.3mf` archives. Full byte comparison of
baseline and modified archives passed for all three sizes.

## Production and browser follow-up

The normal geometry build script now published the optimized candidate:
7,669,594 bytes, SHA-256
`70ef949a93d68f9a9f2ca5b81f47f878ebda62f373d6644cd25a8d17944e505d`.
Baseline was 7,670,726 bytes with SHA-256
`f37b48906375cad0155d2696bb529505b528217798048f8440011ef493bd0a8c`.
Same pinned compiler/optimizer recipe; no language-kernel replacement occurred.

`tools/browser-qualification/3mf-export-benchmark.mjs` accepts baseline and
candidate WASM paths. It uses actual Chrome WASM instances and the repository's
MGV1 codec to export meshes containing 256 or 2,048 disconnected cubes, both
stored and DEFLATE-compressed. The timer covers request allocation/copy, ABI
decode, validation/XML/ZIP work, result copy and native buffer release. Fetch,
compilation, fixture preparation, output comparison and hashing are excluded.
Each variant has three warmups and nine samples. The Vite server provides codec
modules only; this is a browser ABI benchmark, not a UI click-to-download test.

Chrome 156, macOS arm64, two independent runs, no own concurrent builds/tests:

| Cubes | Compression | Before ms | After ms | Repeat before ms | Repeat after ms |
| ---: | --- | ---: | ---: | ---: | ---: |
| 256 | stored | 2.0 | 1.4 | 2.0 | 1.4 |
| 2,048 | stored | 16.2 | 11.1 | 16.4 | 11.3 |
| 256 | DEFLATE | 11.6 | 12.9 | 8.6 | 8.2 |
| 2,048 | DEFLATE | 67.9 | 64.6 | 68.0 | 65.2 |

Stored export improved about 30-31% on these fixtures. The smaller compressed
case is noisy and includes a slower modified result; no reliable improvement
is claimed for it. The large compressed case improves about 4-5%. All sampled
archives were compared byte-for-byte, with matching input and output hashes.
Results: `tmp/performance/3mf-browser/report.json` and
`tmp/performance/3mf-browser-repeat/report.json`.

The Vite production build and production SVG/G-code worker smoke check passed
(`tmp/performance/package-crc-workers/report.json`). Raw WASM shrank by 1,132
bytes, but the final distribution grew by 355 bytes to 5,768,655. Compression
ratios differ; this is not a bundle-size optimization. The unchanged 5,600,000
total gate still fails, while decoded-WASM identity and per-artifact checks pass.

Full regression against this newly published geometry WASM: 3,236 passed and
nine failed across 335 files. Failures remain the engine manifest and frozen
G0/G1 qualification/fingerprint checks; no new functional test failures appeared.
Log: `tmp/performance/package-crc-full-tests.log`. Historical evidence and
budgets were not rewritten to make this run green.

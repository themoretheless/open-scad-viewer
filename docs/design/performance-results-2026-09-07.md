# Результаты оптимизации: 7 сентября 2026

Бенчмарки обнаружили и помогли исправить три существенные проблемы: рост памяти
Manifold при повторной сборке, большой постоянный расход сортировки рёбер маленьких
тел и повторную подготовку одинаковых данных для GPU. На измеренных сценах основная
пауза возникала при анализе/публикации геометрии, а не при исполнении шейдеров.

Измерения локальные: **Apple M4 Max, 16 логических CPU, macOS Darwin 25.6.0,
Node 22.23.2**. GPU: аппаратный Apple Metal 3, Chromium **149.0.7827.55**,
canvas **960 × 640**, DPR 1. Программный адаптер не использовался.

## Что изменилось и что измерено

В таблицах приведены медианы отдельных прогонов. Два числа после изменения —
два независимых прогона. Небольшие различия не считаются доказанным ускорением.

| CPU: полная сборка | До, мс | После, мс | Повтор, мс |
| --- | ---: | ---: | ---: |
| Кронштейн, 540 треугольников | 3,62 | 3,43 | 3,52 |
| Панель с 64 отверстиями, 8460 треугольников | 54,92 | 51,96 | 52,48 |
| 256 отдельных кубов, 3072 треугольника | **59,34** | **11,45** | **11,32** |
| Три сферы в одной сетке, 98 304 треугольника | 164,67 | 160,53 | 163,03 |

Для 256 кубов повторное извлечение рёбер отдельно от сборки сократилось с
**46,54 до 1,52 / 1,50 мс**. CPU-профиль указал на `radixSortEdgeOccurrences`:
таблица из 65 536 счётчиков обрабатывалась даже для нескольких десятков рёбер.
Теперь небольшой поток использует 256 счётчиков: **1 КиБ вместо 256 КиБ**.
Сортировка по полному 32-битному ключу и точный порядок результата сохранены.
Цена дополнительных проходов видна на среднем примере: отдельный повторный
расчёт рёбер вырос с 2,73 до 2,96 / 2,99 мс. Крупная ветка осталась прежней.

| Публикация 128 экземпляров одного GPU-ресурса: время CPU | До, два прогона, мс | После, два прогона, мс |
| --- | ---: | ---: |
| Те же массивы и положения объектов | 22,470 / 22,885 | **0,445 / 0,675** |
| Новые равные массивы и новые объекты положения | 22,005 / 22,490 | **2,615 / 2,825** |
| Новая геометрия с новым содержимым | 11,825 / 11,935 | **2,405 / 2,575** |

Каждая новая сцена подготовлена до измеряемого вызова и используется один раз.
Геометрия общая внутри сцены; экземпляров 128, треугольников на ресурс 4900,
отрисовываемых треугольников 627 200. Контрольный прогон использует сохранённый
исходный renderer через подстановку одного модуля; исходники зависимостей одинаковы.

Изменения renderer:

- Параметры объекта отправляются одной записью 160 байт вместо четырёх.
- Буфер рёбер разделяется экземплярами с одинаковыми вершинным, индексным и
  реберным данными. Кэш пересоздаётся при публикации и очищается при завершении.
- Равные новые данные проверяются по содержимому один раз на общий ресурс в
  публикации; последующие экземпляры используют уже проверенные массивы.
  Совпадения одного идентификатора недостаточно для повторного использования.
- Границы кэшируются для каждой пары геометрия/положение, со слабыми ключами и
  проверкой изменения матрицы. Экземпляры больше не вытесняют друг друга из кэша.
- Небольшие массивы uniform используются повторно; обход непрозрачных объектов
  не создаёт отдельный пустой массив для каждого объекта.

Счётчики GPU устойчивы во всех сравнениях:

| Операция | До | После |
| --- | ---: | ---: |
| Записи при повторной публикации, включая uniform сцены | 513 | **129** |
| Новые буферы при замене геометрии | 258 | **131** |
| Загружено при замене геометрии, байт | 7 667 168 | **199 568** |
| Одинаковые буферы рёбер для 128 экземпляров | 128 | **1** |

Снижение загрузок — **97,4%**. Параметры объектов всё ещё создаются заново:
128 uniform-буферов остаются в каждой публикации. Счётчики не являются показанием
физической видеопамяти. Время GPU-прохода существенно не изменилось, что ожидаемо:
шейдеры и количество нарисованной геометрии сохраняются. Например, для 128
экземпляров проход с рёбрами занимает примерно 1,05 мс; для одной сетки около
200 тысяч треугольников — примерно 0,59 мс с рёбрами. Это синтетический стресс
всех рёбер тесселяции, а не типичное число смысловых рёбер OpenSCAD.

## Подтверждённое исправление памяти

Установленная версия Manifold создаёт фабричный прототип отдельно от прототипа
реальных объектов. Прежняя обёртка сборки мусора перехватывала фабричный прототип,
поэтому результаты преобразований и расчёта нормалей не попадали в очистку.

Новая обёртка следит за реальными объектами, сохраняет получателя вызова и
освобождает ресурсы своего экземпляра WASM. Проверены конструкторы, результаты
массивов, преобразования, нормали, переходы между 2D/3D, ручное удаление,
скрытый промежуточный объект центрированной экструзии и отказ конструктора.
Очистка проверена при успешной сборке, ошибке и отмене.

| 15 одинаковых сборок плотной сетки | До | После |
| --- | --- | --- |
| Реальная ёмкость `WebAssembly.Memory` | **99,69 → 716,13 МиБ** | **99,69 МиБ во всех 15 сборках** |
| Наблюдаемые native-объекты transform/normals после очистки | Не удалены | Все удалены |
| Контрольная сумма геометрии | Одинакова | Одинакова |

WASM не уменьшает уже выделенную ёмкость. Здесь доказательством служат остановка
повторного роста и проверка удаления объектов, а не ожидание возврата памяти к нулю.
Это исправление подтверждённой утечки геометрических объектов; оно не доказывает
отсутствие любых утечек во внутренних структурах стороннего ядра.

## Следующие цели по данным профилей

1. **STL плотной сетки: около 42 мс.** Отдельное семплирование оценивает примерно
   248 МиБ JavaScript-аллокаций на экспорт. Два обхода повторяют преобразование
   вершин, нормали и determinant; создаются временные массивы. Следующий подход:
   скалярная запись и расчёт неизменной матрицы один раз на объект. Нужно сохранить
   отбрасывание вырожденных граней, округление float32, отражения и точные байты.
2. **Плотная геометрия:** отдельно повторённые BVH около 39,5 мс, извлечение рёбер
   около 29,8 мс, хеширование около 18,6 мс. Это диагностические повторы, их нельзя
   складывать с фазой `analyzeMs`. Повтор рёбер использует сварку по позициям;
   исходная сборка получает подсказки сварки от Manifold.
3. **Прозрачность:** в профилях анимации остаются аллокации в
   `transparentOrdering` (`map/sort/map`). Можно исследовать повторное использование
   записей и кэш порядка при неподвижной камере. Порядок должен обновляться при
   движении камеры, смене видимости, прозрачности и геометрии.
4. **Внутренние временные векторы экструзии Manifold:** чтение установленного
   wrapper показывает отдельный вопрос владения polygon-векторами. Это пока
   гипотеза; нужен отдельный длительный сценарий экструзии.

Общий расход JavaScript-аллокаций при анимации по коротким GPU heap-профилям
колебался; количественного заявления о его снижении нет. Во всех проверках
установившегося покоя за 500 мс было ноль отправок кадров, записей и новых
GPU-буферов. Постоянного холостого цикла рендеринга не обнаружено.
